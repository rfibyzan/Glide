# Performance

Both numbers below come from the published native-AOT binary on this machine,
measured by `scripts/bench-query.ps1` and `scripts/measure-memory.ps1`.

## Latency, 100k entries

Snapshot: `artifacts/bench-100k.txt` (synthetic paths, generated by
`scripts/generate-snapshot.ps1`), query `report`, 30 iterations after 5 warmups.

| Version | p50 | p95 | p99 |
|---|---:|---:|---:|
| v0.2.0, first measurement | 31.4 ms | 31.9 ms | 32.8 ms |
| v0.2.0, after fixes | 3.1 ms | 5.2 ms | 6.4 ms |

Budget: p95 under 30 ms. The first measurement failed the gate, which is how the
regression was found.

### What changed

1. Match positions are computed only for rows that survive into the top list.
   Before, every matching entry allocated an `int[]`, so a query matching 100k
   entries allocated 100k arrays per keystroke.
2. The insertion path checks the worst row first and rejects immediately. Before,
   a candidate worse than the whole list still walked all 50 rows.
3. Scans above 16,384 entries are split across up to 8 workers. Each worker keeps
   its own top list, and the lists are merged with the same comparator, so the
   result order stays deterministic.

## Memory with a loaded snapshot

100k entries resident, idle, 25 samples:

| Metric | Value |
|---|---:|
| Average | 31.7 MB |
| p95 | 32.9 MB |
| Budget | 50 MB |

That is 1.9 MB of working set for runtime and strings per 10k entries, with the
whole `FileEntry[]` and its path strings held on the heap. The v0.4.0 index moves
that data into a file that is streamed during a query, so memory no longer
scales with the number of indexed entries.

## The window, v0.3.0

The same 100k snapshot, this time inside the launcher:

| Case | Working set |
|---|---:|
| Hidden after load | 33.8 MB |
| Visible, painting, results shown | 38.5 MB |
| Folder scan of a small tree (`D:\Glide`) | 14.3 MB |

`scripts/ui-smoke.ps1` drives the published binary: it presses Ctrl+Alt+Space,
checks the window takes focus, posts keystrokes, screenshots the result, revokes
focus and checks the window hides, then reopens and closes it with Escape.

Two bugs that only a real desktop could show up:

1. `PlaceWindow` used `SWP_SHOWWINDOW`, so the window became active before
   `_visible` and `_shownAt` were set. Deactivation then looked like a spurious
   event and the launcher stopped hiding.
2. `AttachThreadInput` was used unconditionally to grab the foreground. The
   window looked focused to the window manager while the thread had no active
   window, so no `WM_ACTIVATE` arrived on deactivation. The plain
   `SetForegroundWindow` call works because `WM_HOTKEY` already grants foreground
   rights; attaching is now only the fallback.

Hiding is guarded by a 400 ms timer: after `Show()` the window verifies once that
it really owns the foreground and hides itself if it does not. That covers both a
refused foreground request and an immediate focus steal without leaving a topmost
window floating over other applications.

## Folder scan cap

Real profile paths average longer than the synthetic bench paths, and a string
per entry does not fit the budget at full scale:

| Entries | Working set |
|---:|---:|
| 60,000 | 37.4 MB |
| 75,000 | 43.8 MB |
| 100,000 | 53.2 MB |
| 200,000 | 88.2 MB |

The default cap is 75,000. Scanning 200,000 entries takes 7.6 s and 88 MB; the
cap is the honest v0.3 boundary until the compact store lands.

## The on-disk index, v0.4.0

`--index-build` turns a snapshot into a `.gidx` file. A record is a flags byte,
the UTF-8 path, and a NUL terminator, so an entry costs 50 bytes for the
synthetic 50-byte paths above. Building 1M entries takes 83 ms.

Queries stream the file with `RandomAccess`, one handle per worker: reads on a
single synchronous handle are serialized by the file object, and opening the
handle for overlapped I/O instead made `RandomAccess` fault under NativeAOT.
With one handle, 50 MB read in 16 ms; with one per worker, 9 ms. Each of up to 8
workers holds a 128 KB buffer and keeps its own top list, merged with the shared
comparator.

| Query, 1M entries | p50 | p95 | p99 |
|---|---:|---:|---:|
| `report` | 19.2 ms | 22.6 ms | 25.0 ms |
| `project1` | 21.5 ms | 24.1 ms | 26.2 ms |
| `users documents` | 22.7 ms | 25.8 ms | 27.4 ms |
| `zzzzzz` (no match) | 9.8 ms | 10.8 ms | 11.3 ms |
| `report`, 100k entries | 3.4 ms | 4.2 ms | — |

Budget: p95 under 30 ms at 1M entries, under 10 ms at 100k. Numbers are the
median p95 of five runs of 60 queries after 15 warmups.

Three things took the 1M case from 38 ms to 22 ms:

1. ASCII paths are scored as bytes, so a query never decodes a million strings;
   only the 50 winners become strings.
2. The index stores an ASCII bit per record. Before, every query ran an
   `Ascii.IsValid` pass over every path just to choose a decoder.
3. Scoring searches with vectorized `IndexOfAny` on the folded byte and its
   uppercase twin instead of folding each byte in a scalar loop. The no-match
   query fell from 22 ms to 10 ms, which is close to the 9 ms the file read alone
   costs.

The same rules rank both backends: `EntryScorer` holds the tier bonuses and the
compare order, and the index tests assert that byte scoring, character scoring,
and the in-memory engine produce identical results.

## Memory while querying the index

Streaming a 1M-entry index 600 times in one process: 36.8 MB average, 39.2 MB
peak. The read buffers are pooled and reused; the top list holds at most 50
paths.
