# Performance

Both numbers below come from the published native-AOT binary on this machine,
measured by `scripts/bench-query.ps1` and `scripts/measure-memory.ps1`.

## Latency, 100k entries

Snapshot: `artifacts/bench-100k.txt` (synthetic paths, generated by
`scripts/generate-snapshot.ps1`), query `report`, 30 iterations after 5 warmups.

| Version | p50 | p95 | p99 |
|---|---:|---:|---:|
| v0.2.0, first measurement | 31.4 ms | 31.9 ms | 32.8 ms |
| v0.2.0, after fixes | 3.1 ms | 5.2 ms | 6.4 ms |

Budget: p95 under 30 ms. The first measurement failed the gate, which is how the
regression was found.

### What changed

1. Match positions are computed only for rows that survive into the top list.
   Before, every matching entry allocated an `int[]`, so a query matching 100k
   entries allocated 100k arrays per keystroke.
2. The insertion path checks the worst row first and rejects immediately. Before,
   a candidate worse than the whole list still walked all 50 rows.
3. Scans above 16,384 entries are split across up to 8 workers. Each worker keeps
   its own top list, and the lists are merged with the same comparator, so the
   result order stays deterministic.

## Memory with a loaded snapshot

100k entries resident, idle, 25 samples:

| Metric | Value |
|---|---:|
| Average | 31.7 MB |
| p95 | 32.9 MB |
| Budget | 50 MB |

That is 1.9 MB of working set for runtime and strings per 10k entries, with the
whole `FileEntry[]` and its path strings held on the heap. The USN index in
v0.4.0 moves that data into a memory-mapped file so it no longer scales with the
heap.
